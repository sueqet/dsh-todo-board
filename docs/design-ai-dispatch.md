# 方案：让 AI 自己编辑并派发任务（MCP / 规则）

> 状态：**仅规划，本版不实现**。用户已定的权限模型见 §8；强制机制见 §9；
> **两条实测到的绕过通道见 §10 与 §12**（这两条是实现前必须先定掉的）；决策清单见 §13。
> 用户目标（2026-09-25 原话要点）：用户通过**一个入口/一个提示词**，让 DSH 的一个会话
> **自动使用我们的工具**，把**长任务 / 分段式任务 / 多个任务**分配给**其他会话** ——
> 也就是**允许 AI 自己编辑 todo 和派发任务**。

---

## 0. 结论先行

**1. 权限不用自己造 —— DSH 有原生审批通道，而且本机已经装好了。**（§9，实测）

`tools/pre-execute` 这个 waterfall 可以在**注册表层**把一次工具调用判成 `ask`，
由 `dsh-user-approval` 弹给用户；**没有审批通道时降级为拒绝**（fail-closed）。
我实测确认：读放行、写被拦、模型绕不过去。`dsh-base` 已挂 `dsh-user-approval`
（policy 默认 `ask`），`dsh-web-app` 已挂 `ui-approval` —— **UI 也是现成的**。

**2. 但有两个坏消息，都是实测出来的 —— 它们把"加个审批"变成了"先做通道收敛"。**

**2a. AI 今天就已经能自己派发**（§10）：`add` 接受 `mode`，而回合结束钩子会自动派发
同目录下第一条非 `remind` 条目。实测：模型调一次 `add {mode:"resume"}`，回合结束时任务
就被派给会话了，**全程不需要用户动作**。

**2b. 工具上的审批门可以被 HTTP 路由绕过**（§12）：同一批写操作还挂在
`/dsh-todo-board/api` 上，而那条路由接受任何本机客户端的写请求（`Host` 回环即放行 ——
它是防 rebinding/CSRF 的浏览器围栏，**不是鉴权层**）。**AI 有 shell，所以它能绕过。**

**3. 两条合起来说明本项真正的第一件事。**
> 任何"AI 不该做的事"，只要还有一个 AI 够得到的等价通道，审批就是装饰。

所以实现顺序应当是 **决策 H（通道收敛）→ 决策 E（封侧门）→ 加动作与审批 → 入口**（§4）。

**4. 另外两条既有判断仍然成立**（§2、§4 第 3 步）：派发目标走**用户可见的会话**而不是
`ctx.subagents`（子代理不进侧栏、且用户不能对它说话）；提示词必须把我们的 `todo_board`
和内置 `todo_write` 说清楚，否则模型会在两套"待办"之间精神分裂。

**5. "MCP" 不该用**（§7）：MCP 工具在 DSH 里同样是注册进 `ctx.tools` 的原生工具，
差别只在执行时拿不到 `exec.agent` —— 而本插件的语义全押在它上面。

## 1. 现状：已经有什么、缺什么

### 已有

- 模型工具 `todo_board`：`list / add / done / reopen / note / schedule`
  （`lib/index.js` 的 `TOOL_PARAMETERS`）。
- 回合结束钩子 `agent/turn-stopping`：按从上到下的顺序，
  派发**同目录**下一条未派发的自动模式待办。
- 两条派发通道：`resume`（`followup`/`steer` 注入当前会话）与 `newSession`
  （`ctx.root` + `agents.create` + `agentPresets.mount`，并登记进工作区）。
- 失败处理已经成熟：`markLost` + 退避重试，且不会卡死 host。
- **v0.9.0 新增**：日志与信任围栏（见 `design-log-view.md`）—— 派发失败现在会留痕，
  这对本项的调试很重要。

### 缺什么（对照目标）

| 目标 | 现状 | 缺口 |
| --- | --- | --- |
| AI 自己**编辑** todo | 能 add/done/note/schedule | **不能改模式、不能改目录、不能排序** —— 面板有 `patch`/`reorder`，模型够不到 |
| AI 自己**派发** | **`add` + `mode` + 回合钩子这条侧门已经能派**（§10） | 没有"现在就派发这一条"的动作（面板的 `run` 模型够不到）；**侧门本身是个待封的口子** |
| **长任务/分段** | 无 | 没有"把一个大任务拆成多条并串起来"的概念 |
| **多个任务** | 一次只派一条（`nextUndispatched` 单条） | 没有批量/并行派发与并发上限 |
| **一个入口/一个提示词** | 只有 systemPrompt 段落 | 没有 `/` 命令入口，也没有 Skill |
| **写操作要用户批准** | **完全没有** | 需要接上 `tools/pre-execute` + 审批通道（§9） |

## 2. 关键事实：为什么建议**不用** `ctx.subagents`

这是本方案最重要的判断，依据是我在本机的实测与源码核对：

### 2.1 子代理**不进会话列表**，用户**看不见**

`dsh-agent` 的 `list()` 文档写得很明确（`lib/types/index.d.ts:355-358`）：

> `list(): Agent[]` — **All live top-level agents** in registration order.
> A top-level agent was created **without an owning agent context**.

子代理是**有 owning agent context** 的，所以**不在 `list()` 里**。
新的子代理会话带 `parentSessionId` / `origin: 'subagent'` / `delegationDepth`
（`dsh-agent`、`dsh-client-ui-subagent`），是**挂在父会话下的血缘**，不是侧栏里的一行。

### 2.2 子代理对用户**是只读的**

`dsh-client-ui-subagent` 明确实现了"只读作曲器"：
`SubagentReadOnlyComposer`，其文案（`lib/client.js:805-808`）：

- `readonly.oneShot.body`: "One-shot tasks **do not accept follow-ups**; review the full
  execution record here."
- `readonly.body`: "The parent session is offline; reopen it to continue sending messages."

即：**用户不能直接往子代理里打字**。one-shot 类型的子代理更是**设计上就不接受后续消息**。

### 2.3 所以

本插件的产品定位是"**用户看得见、能验收、能插手**的任务板"。
把任务派给子代理 = 把任务送进一个**用户看不见、也不能直接干预**的地方，
这和插件存在的理由是冲突的。

> 子代理不是不能用，而是**它解决的是另一个问题**：让一个会话在内部并行拆解工作、
> 最后汇总。那属于"会话内部的执行细节"。我们要做的是"**跨会话的任务分发**"，
> 用户要能看到"这件事在哪个会话里、跑到哪一步了"。
>
> 两者可以**共存**：主会话自己用子代理并行干活（harness 原生能力，模型本来就有
> `subagent` / `send_message` / `list_agents` 工具），而**任务板负责把任务分给
> 用户可见的会话**。不要用子代理去实现任务板。

## 3. 需要你拍板的架构决策

### 决策 A：派发目标用哪种会话？

| | A1. 本插件现有方式（推荐） | A2. `ctx.subagents` |
| --- | --- | --- |
| 用什么 | `ctx.root.get('agents').create(...)` + `agentPresets.mount` | `ctx.subagents.startContinuable(...)` |
| 用户可见 | ✅ 侧栏正常一行，可打开、可打字、可验收 | ❌ 只在父会话血缘里，**且只读** |
| 与现有代码 | 复用 `spawnSession`，改动小 | 新通道，`resume`/`newSession` 两模式要重新映射 |
| 并发控制 | 我们自己定 | harness 有 `maxDepth`（`SubagentDepthError`）等 |
| 生命周期 | 已实现：挂 `ctx.root`，脱离插件生命周期 | 由父会话持有，父会话没了就不可续 |
| 适合 | **用户可验收的跨会话任务** | 会话内部并行、一次性取结果 |

**我的建议：A1。** 与插件定位一致，且已有代码基本够用。
如果将来你想要"会话内部并行"，那是 subagent 的活，**不必**由本插件承担。

### 决策 B：允许 AI 自己 add 之后**立刻自己派发**吗？

> **已由用户拍板（§8），且比 B1 更严格**：任何写操作都要先申请权限。
> 下面保留当初的权衡记录，但**结论以 §8 为准**。

这条是**风险边界**，不是技术问题：

- **B1（推荐）**：AI 只能派发**用户已创建/已认可**的待办；AI 自己 `add` 的条目默认
  是 `remind`（只提醒），要派发必须用户改模式或点 ▶。
- **B2**：AI 可以自己 add 且自己派发 → 等于允许模型**自行扩大执行面**，
  在无人确认的情况下开新会话、烧 token、改文件。

建议 B1，并给一个显式开关让你按需放开。

**后续（§10）发现**：B1 描述的"AI 自己 `add` 的条目默认是 `remind`"**今天并没有做到** ——
`add` 是接受 `mode` 的，所以 B2 的行为实际上已经可达。这条不是被否决了，而是**还没接上**。

### 决策 C：并发上限与目录白名单

- 同时最多几个 `newSession` 派发在跑？（现有代码一次只派一条，我建议默认 1–2，可配）
- 是否限制只能派发到某些目录？

### 决策 D：长任务的"分段"用什么表达？

三种做法，语义差别很大：

1. **多条待办 + 顺序**（推荐）：一个大任务拆成 N 条待办，靠现有"从上到下就是执行顺序"
   串起来。**零新概念**，用户可拖动、可删、可插队 —— 复用全部现有 UI 与调度。
2. **父子待办**：给待办加 `parentId`，面板折叠显示。表达力强，但要改板文件 schema、
   面板渲染、调度取任务的规则（"父条目何时算完成？"），成本高一个量级。
3. **不表达**：让模型自己在一条待办里写"第一步…第二步…"。最省事，但用户看不到进度，
   也失去了本插件最大的价值。

建议 1 起步；确实不够用时再考虑 2。

## 4. 建议的实现路线（待决策后）

> **注意**：下面的步骤写于用户定下权限模型（§8）之前，也早于两条绕过通道的发现。
> 现在实现顺序应当是：
> **决策 H（通道收敛，§12）→ 第 1 步（补动作 + 挂审批门）→ 第 0 步 E1（可选加固）→ 第 2 步（入口）**。
> 理由：**先有"AI 够得到的写入口只有一处"，审批才有意义**；
> 而 E1 已降级为可选（§11）—— 审批门装在 `add` 上就已经是决策点。

### 第 0 步（可选加固）：只收紧**模型**那条 `add` 路径

**注意范围**：只改**工具** `add`，**面板的 `create` 一个字都不动** ——
用户必须仍然能直接建"续跑 / 新会话"的待办。

做法：工具 `add` 不接受 `mode`（一律 `remind`），要自动跑必须再走一次要审批的 `update`。
只改工具参数表与工具 `add` 的实现，**不碰调度、不碰路由**。

**这一步是可选的**（见 §11 的重新评估）：如果审批门已经装在 `add` 上，
用户在弹窗里就能看见并拒绝 `mode:"resume"`，E1 只是把"自动执行"变成一次专门的批准。
**先上审批门，E1 留给你定。**

### 第 1 步：补齐模型对板子的写权限（最小、风险最低）

给 `todo_board` 增加动作，**让模型能做的和面板能做的对齐**（现在模型是残缺的）：

| 新动作 | 作用 | 建议约束 |
| --- | --- | --- |
| `update` | 改 `mode` / `dir` / `title` / `note` | **要审批**（§9）；改到 `newSession` 尤其如此 |
| `reorder` | 传 id 数组设定顺序 | **要审批**；只允许重排**同目录**内的相对顺序，避免模型把别人的队列搅乱 |
| `dispatch` | 立即派发一条（等价面板 ▶） | **要审批**；仅当该条 `state === 'pending'`；沿用现有 `dispatch()`，自动获得 `markLost` 与退避 |

`dispatch` 直接复用 `runTodo()`，所以**失败处理、图片校验、会话绑定全都现成**，
这是最小改动、最大复用的那一步。

**审批怎么接**：注册**一个** `tools/pre-execute` 监听器，只对 `todo_board` 的写动作返回
`{kind:'ask', reason}`，`list` 走 `next()`。要**白名单式**判断（枚举哪些动作算写），
不要黑名单式（漏一个就是一个后门）—— 详见 §9.5 的现成先例。

### 第 2 步：入口（Skill + `/` 命令，两者都要）

**手册用 Skill**（§7.4）：`ctx.skills.register()` 注册一份"怎么用任务板干活"的说明，
模型按需加载、用户可 `/技能名` 直达。

**确定性入口用命令**：`ctx.commands.register({ name, description, input, handler })` ——
先例是 `dsh-command-goal`。`handler` 拿到的 `invocation` 有
`{ agent, rawInput, attachments, signal }`。

建议一个 `/todo` 命令，几种用法：

- `/todo 拆解 <目标>`：读当前目录的板子 → 把目标拆成若干条待办 → **列给你看并等确认**。
- `/todo 派发`：把当前目录下已就绪的自动模式待办按顺序派出去。
- `/todo 状态`：汇总各条的状态。

**关键设计点**：`handler` 是**在会话里执行**的，它可以直接 `agent.followup(...)` 注入一段
结构化提示词，让模型去做拆解 —— 这就是"一个提示词入口"最省力的实现，
不必自己写一个拆解器。


### 第 3 步：与 DSH 原生机制划清界限（重要，避免两套状态打架）

本机 DSH 已有这些"长任务"机制，必须明确我们不重复造：

| 机制 | 谁创建 | 模型工具 | 用户可见 | 跨重启 | 定位 |
| --- | --- | --- | --- | --- | --- |
| `todo_write`（**内置**） | 模型 | `todo_write` | 会话内渲染 | 随会话事件 | **单个会话内**的步骤清单 |
| `goal` | 用户 `/goal` 或模型 | `goal` 工具 | goal 面板 | 会话事件源 | **同一会话**的长目标续跑 |
| `ralph` | 用户 | `ralph` | 有 UI | 脚本固定 | 固定脚本的**全新 agent** 迭代 |
| `workflow` | 模型 | `workflow` | 有 UI | 否 | 一次性**扇出**多子代理 |
| `subagent` | 模型 | `subagent`/`send_message`/`list_agents` | 父会话血缘（只读） | 父会话在则可续 | 会话**内部**并行 |
| **本插件** | **用户**（+将来 AI） | `todo_board` | **侧栏会话 + 浮窗板** | ✅ 板文件 | **跨会话、用户可验收**的任务分发 |

**本插件的独特价值 = "跨会话 + 用户可见可验收 + 落盘持久"**。
任何让它变成"另一种会话内待办"的设计，都是在和内置 `todo_write` 抢地盘。

因此提示词段落（`lib/index.js:1142-1152`）**必须加一段**说明两者的区别，例如：
> 你另有一个 `todo_write` 工具，那是**你自己在本会话内的步骤清单**，会话结束就没了；
> `todo_board` 是**用户的跨会话任务板**，会落盘、会派发给其他会话、由用户验收。不要混用。

### 第 4 步：拆解与分段的行为规范

写进提示词段落（而不是靠模型自由发挥）：

- 拆解粒度：一条待办 = **一次能做完并验收**的事；太大的继续拆。
- 拆完**先列出来等用户确认**（决策 B1），不要直接派发。
- 派发顺序 = 板子从上到下；不要跳序。
- 每完成一条立刻 `done`，再取同目录下一条（现有的自动接续已经这么做）。

## 5. 风险清单

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **模型自己派发 = 自行扩大执行面** | 无人确认就开新会话、烧 token、改文件 | **§9 的审批门**（注册表级，绕不过）+ 决策 E 封侧门；并发上限；目录白名单 |
| **侧门已开着**（§10） | `add` + `mode` + 回合钩子 = 今天就能无人派发 | 审批门装在 `add` 上；E1（**只改工具侧**，不动面板）作为可选加固 |
| 与内置 `todo_write` 概念混淆 | 模型可能把两者当同一个 | 提示词明确区分（§4 第 3 步） |
| 一次派发太多 | 现有调度一次只派一条，批量派发是新路径 | 复用 `firing` 去重集合与 `markLost` 退避；加并发上限 |
| 派发循环 | AI 派发的任务又让 AI 派发 … | 派发产生的会话**不应**再自动开新会话（该模式下禁用 `newSession` 自动派发） |
| 任务板语义被稀释 | 若 AI 随意 add，板子变成模型的草稿纸，用户看不懂 | AI 自建的条目**标注来源**并在面板上区分显示 |
| **审批打断回合** | `ask` 会同步等裁决；用户不在时回合挂住（`policy: never` 时确定性拒绝） | 与决策 C/F 一起定；见 §13 |
| **路由绕过审批**（§12） | HTTP 路由接受全部写操作，AI 有 shell 就能绕过工具上的门 | 决策 H |
| **自动路径不受审批保护** | `fireDue`（定时）与回合钩子**不在回合内**，`approval.request()` 用不了（§10.3） | 让它们只作用于**已存在且已获批**的条目；这正是 E1 的另一个好处 |

## 7. 澄清："MCP" 到底该不该用（2026-09-25 调研结论）

用户的疑问原话是："我不知道通过 MCP 实现，和直接让模型进行操作的区别。
我认为同样是把一个工具的操作手册交给 AI。"

**"手册部分相同"这个判断是对的；差别不在手册，在执行时能拿到什么。**

### 7.1 模型侧：两种做法**完全等价**

`dsh-mcp-client` 并不是另一套机制 —— 它把 MCP 工具**注册进同一个 `ctx.tools` 注册表**：

- `lib/tools.d.ts` 的 `syncTools(client, ctx, ...)` 就是往 `ctx.tools.register` 里塞；
- `lib/index.js` 的 `callToolUncached(client, rawName, args, exec, opts)` 走的是同一个执行管道。

所以 MCP 工具同样是**原生工具**：同样的 token 成本（`README.md` 明说
"the server-qualified name adds tokens to every tool definition and call"）、
同样的 KV cache 行为、同一份 loader。**"都是把操作手册交给 AI"这句是准确的。**

### 7.2 真正的差别：MCP 那次调用**只传 `{name, arguments}`**

- MCP 调用线路上只有 `{name, arguments}` + 一个 abort signal，**没有 agent、没有 cwd、没有 session**。
- DSH 的 MCP client 只宣告 `capabilities: {}`，全树 **`roots` 零命中** ——
  连"我当前工作目录是哪儿"这条标准 MCP 通道都没实现。
- 而本插件的核心语义**恰好全押在这些东西上**：

| `todo_board` 依赖 | 位置 |
| --- | --- |
| 调用者工作目录（决定是哪块板子） | `exec.agent.session.header.cwd` |
| 派发要开新会话 | `ctx.get('agents')` + `agents.create` |
| preset / 附件库 / 源会话的模型选择 | `ctx.get('agentPresets')`、`ctx.get('attachments')`、`modelSelection(source)` |

一个**进程外**的 MCP server 一个都拿不到。真走 MCP，就得让 server 再反向 HTTP 调回 host ——
绕一圈把自己变成自己的客户端，同时**永久丢掉 `exec.agent`**。

### 7.3 还有一条硬事实：DSH 全树没有 MCP server 端

`@modelcontextprotocol/sdk` 只被 import 了四个 **client** 子路径
（`client/index`、`client/stdio`、`client/streamableHttp`、`types`），MCP 相关包**只有
`dsh-mcp-client` 一个**。做 MCP server 意味着另起进程 + 独立生命周期 + 自建回 host 的通道，
成本高一个量级，收益是负的。

### 7.4 结论：手册用 Skill，入口用命令，干活用原生工具

| 诉求 | 机制 | 为什么 |
| --- | --- | --- |
| 把操作手册交给 AI | **Skill**（`ctx.skills.register()`） | 按需加载、不常驻上下文；用户可 `/技能名` 直达。运行时注册落在**全局层**，标准 preset 的每个会话都看得到（`dsh-skill` 的 layer 合并） |
| 确定性入口 | `ctx.commands.register`（先例 `dsh-command-goal`） | handler **在会话内执行**，可直接 `agent.followup()` 注入结构化提示，不必自己写拆解器 |
| 真正干活 | **现有原生 `todo_board` 工具**（补动作） | 只有它拿得到 `exec.agent` |

**MCP 在这一版没有任何位置。** MCP 是给"能力本来就住在进程外"的工具用的
（GitHub、context7、demox…），本插件不是。

## 8. 用户已定的权限模型（2026-09-25）

用户原话（第二次表述把**边界**说得更准，以这段为准）：

> 我希望 AI 在修改 todo 面板（当前功能之外的所有功能，包括创建 todo、编辑、
> 更改模式/目录/标题/排序、派发）时，需要明确向用户申请权限。之后就可以写入 todo 面板，
> 然后需要用户开始执行，之后就是我们之前的逻辑，AI 继续执行 todo 面板里的其他 todo，
> 直到完成所有 todo。

> AI 只有申请编辑的时候需要审批，后期都是我们现有的逻辑，自动派发下一个任务。
> **第一个任务的派发仍然要用户自己开始。**

### 8.1 边界：审批挡的是"改板子"，不挡"跑任务"

| 阶段 | 谁发起 | 要不要审批 |
| --- | --- | --- |
| AI **写入板子**（创建 / 编辑 / 改模式·目录·标题 / 排序） | AI | ✅ **要** |
| **第一条**任务开始执行 | **用户**（点 ▶ / `/todo 派发`） | 不需要 —— 用户点按**就是**授权 |
| 之后的接续（做完一条 → 取同目录下一条） | 现有 `turn-stopping` 逻辑 | **不需要** —— 这正是它该自动做的事 |

这条区分很关键，它决定了两件事的做法：

1. **封侧门（决策 E）不等于禁止自动接续。** 我们只把"AI 顺手把模式改成自动"
   这条**写入**路径收进审批；接续逻辑本身照旧。
2. **路由（决策 H）要挡的是写操作，不是整条路由。**
   面板的 ▶ 是"用户点按"，必须继续直连可用。

### 8.2 拆成可实现的三条

1. **写操作一律先申请**：创建 / 编辑标题 / 改备注 / 改模式 / 改目录 / 改排序 / 定时
   —— 都是"改板子"，都要显式获批。**读（list）不需要。**
2. **获批后才写入**：审批是写入的前置，不是事后通知。
3. **跑任务不经审批**：用户点 ▶ 启动第一条；之后的接续由现有逻辑自动进行。

**"派发"要不要审批，按上面这句修正**：用户点按的派发不需要（那就是授权本身）；
但**AI 自己发起的**派发仍要（否则等于绕过"第一条由用户开始"）。
即：`dispatch` 动作**要审批**，而面板的 ▶ **不要** —— 两者本来就是不同入口。

对照 §4 第 1 步的"补齐模型写权限"：

| 新动作 | 审批要求 |
| --- | --- |
| `update`（mode/dir/title/note） | **需要** |
| `reorder` | **需要** |
| `add` | **需要**（AI 自建条目还要**标注来源**，见 §5 风险表） |
| `dispatch`（AI 发起） | **需要**（对应"第一条由用户开始"） |
| 面板的 ▶ / 用户点按 | **不需要** |
| `list` | **不需要** |

**审批粒度**：接上 `ask` 即"逐次"；放宽由用户用 DSH 现成的 `/permission` 档位自己决定（§9.3）。

## 9. 权限怎么强制：用 DSH 原生的审批通道（**实测**）

这是本次调研最有价值的一条：**不需要自己造确认弹窗，也不该造。**

### 9.1 机制：`tools/pre-execute` 返回 `ask`

`dsh-tools` 的注册表管线上有一个 waterfall：

```js
'tools/pre-execute'(this, exec, next): Promise<PreToolDecision>
```

`PreToolDecision` 是 `{kind:'allow'} | {kind:'deny', reason} | {kind:'ask', reason?}`，
默认（`next()`）是 `allow`。返回 `ask` 之后由 `serviceAsk` 交给审批服务裁决（`dsh-tools/lib/index.js:3116-3117`）。

**为什么这条比"在工具里自己弹窗"强**：它作用在**注册表层**，在任何工具体执行之前，
所以模型**没有绕过的路径** —— 不是"提示词请它先问"，而是"不问就执行不了"。而且
`deny` 的结果是一条真正的失败结果，模型会**明确看到自己被拒绝了**（`Error: the user rejected tool "todo_board"`），
而不是以为写成功了。

### 9.2 三层 fail-closed（`dsh-tools/lib/index.js:3314-3356`）

| 情况 | 结果 |
| --- | --- |
| 本部署没装审批服务（`ctx.get('approval')` 为空） | **拒绝**：`requires approval, but no approval channel is available` |
| 调用没有 agent（无从路由到会话/UI） | **拒绝**：`has no agent to route it through` |
| 裁决不是 `allowed-once` | **拒绝**，且三种非授权各有不同措辞（`rejected` / `cancelled` / `unavailable`），模型能分清"人说不"和"没有审批通道" |

`dsh-user-approval` 的模块注释原话：**"Missing answerers fail closed; grants apply only to
the requested action."** 一次授权只对**这一次调用**有效 —— 正好是"逐次申请"的语义。

### 9.3 本机已经装好了（所以 §13 决策 F 才有得选）

```
dsh-base/cordis.patch.yml    - id: approval   name: '@deepseek-ai/dsh-user-approval'
                               policy: (DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'
dsh-base/cordis.patch.yml    - id: permission name: '@deepseek-ai/dsh-permission-presets'
dsh-web-app/cordis.patch.yml - id: ui-approval name: '@deepseek-ai/dsh-client-ui-approval'
```

**UI 都是现成的**：连到 `ui-approval` 就会用 GUI 里那套审批面板，不需要我们画。
注意 `policy` 的两个档：`danger-full-access` 下是 **`never`**（= 每个 ask 都确定性地变成 `rejected`），
也就是"我现在全权信任，别问我"；其余档是 `ask`。

**而且"会话级授权"DSH 已经提供了 —— 不需要我们自己发明**：`dsh-permission-presets`
把 sandbox 与 approval 打包成三档（`read-only` / `workspace-write` / `danger-full-access`），
读侧是 `permissions` 会话投影，**写侧是 `/permission` 命令**。也就是说用户可以自己切换
"这个会话现在要不要问我"，而且这个选择是**会话级、可回放**的（落进会话日志的
`approval/policy` 事件，最后一次为准）。

这条让**决策 F 变简单了**：我们不需要实现"记住已授权到什么时候"，
只需要接上 `ask`，把粒度交给 DSH 现成的档位。**逐次确认是默认，放宽由用户用 `/permission` 自己决定。**

一条要留意的联动：`never` 策略下模型会收到一句运行时说明
（`NEVER_SENTENCE`）："审批提示已在此会话禁用，需要审批的操作会被自动拒绝 —— 不要再申请提权"。
所以 `never` 不是"我们的门失效了"，而是"我们的门变成了一道确定性的墙"——
写入会被拒、模型也知道别试。**对安全是好事，对可用性要你在需要自动跑的时候自己切档。**


### 9.4 实测（在真实 `ToolRuntime` 上跑过）

我在真实 cordis + 真实 `ToolRuntime` 上挂了一个注册 `todo_board` 的插件，
并注册 `tools/pre-execute` 监听器：`list` 放行，其余动作 `ask`。结果：

```
--- read (should pass) ---
{"isError":false,"text":"[{\"type\":\"text\",\"text\":\"ran list\"}]"}
--- write, no approval channel (should FAIL CLOSED) ---
{"isError":true,"text":"[{\"type\":\"text\",\"text\":\"Error: AI 想写入待办板\"}]"}
--- write, no agent (should deny) ---
{"isError":true,"text":"[{\"type\":\"text\",\"text\":\"Error: AI 想写入待办板\"}]"}
```

结论：**读放行、写被拦、fail-closed 生效**。挂上 `dsh-user-approval` 之后，
一次 `ask` 会真的走 `approval/request` 去要裁决 —— 但**必须在回合内**（见 §10.3）。

### 9.5 现成先例

`dsh-hooks-claude-code`（`lib/index.js:260` 附近）就是这么干的：
把 `PreToolUse` hook 的 `"ask"` 直接映射成 `{kind:'ask', reason}`。
照它的写法即可，不必自己设计。

## 10. **坏消息：AI 今天就已经能自己派发**（实测）

这条比"机制怎么接"更要紧，因为它决定方案的范围。

### 10.1 侧门在哪

1. `add` 动作接受 `mode`（`remind` / **`resume`** / **`newSession`**）；
2. `agent/turn-stopping` 钩子会在回合结束时，派发**同目录下第一条 `dispatchedAt === 0` 且非 `remind`** 的待办；
3. 提示词段落**现在就允许**模型 `action="add"`。

三者连起来：**模型 `add` 一条 `mode:"resume"` 的待办，回合结束时它就被派发出去了，不需要用户任何动作。**

### 10.2 实测

```
=== 1. AI adds a todo with mode="resume" (no user involved) ===
add ok: da6ddb19-… mode: resume

=== 2. The AI turn ends ===
messages the agent received: 1
  -> 【TODO 板 · 自动接续】 / 待办：AI 自己造的任务

BYPASS CONFIRMED: the model created and dispatched a task with no user action
```

`mode:"newSession"` 同理，走的是 `spawnSession`（会开一个新会话）。

### 10.3 顺带实测到的一条实现约束

`approval.request()` **要求回合是开着的**，否则直接抛：

> `approval.request() outside an open turn: the approval/asked + approval/decided audit pair
> must be turn-enclosed (a bare event between turns is crash-tail garbage on reload).`

这有两个含义：
- **好事**：审批天然被约束在"某个回合里"，审计事件成对落进会话日志，可回放；
- **要小心**：任何**不在回合内**的写入路径都不能靠审批保护 —— 尤其是**定时派发**
  （`fireDue` 是定时器触发的，不是一个回合）和**回合结束钩子**本身。
  这两处要么不写板，要么用别的手段（决策 E，§11）。

### 10.4 这条为什么必须在实现前定

只给将来的 `dispatch` 动作加审批，**等于给一扇已经开着的门旁边再加一把锁**：

- 用户以为"AI 要派发会先问我"，但模型走 `add` 就能绕过；
- 而这条侧门**今天就在生产里开着**，不是本项引入的。

所以决策 E（§13）是**先决条件**，不是可选项。而且 §12 表明它还**不是全部** ——
同一个"等价通道"问题在 HTTP 路由上又出现了一次。

## 11. 决策 E 的候选（封 `add` + `mode` 侧门）

> 决策清单已统一到 §13（含 §12 的路由绕过）。本节只展开 E 的候选。

### ⚠ E1 的原表述是错的，已更正

我原先写的是"`add` 不再接受 `mode`（**新建一律 `remind`**）"。用户反对：

> **"新建一律 remind？这是个坏决策，因为用户自己也无法直接添加续跑/新会话的 todo 了。"**

**这个反对成立，而且指出的是范围错误。** `add`（模型工具）与 `create`（面板路由）是
**两条独立路径**（`lib/index.js` 的 `action === 'add'` 与 `async function createTodo`）——
但"新建一律 remind"若被实现成**共享约束**，就会把面板的模式按钮一起废掉：
用户从此没法直接建一条"续跑"的待办。**那是把一个安全收紧做成了功能倒退。**

### 更正后的 E1：只收紧**模型**那条路径

| 路径 | 谁在用 | 该不该限制 `mode` |
| --- | --- | --- |
| 面板 `create`（HTTP 路由） | **用户**点按 | ❌ **不该限制** —— 用户建一条"续跑"本来就是他的权利 |
| 工具 `add` | **模型** | ✅ 限制：不接受 `mode`，一律 `remind`；要自动跑必须再走一次要审批的 `update` |

这样侧门关上的同时，**面板完全不受影响**。

### 更重要的追问：E1 现在还必要吗？

写 §9 时我漏看了一条：**审批面板会显示这次调用的具体内容。**
`dsh-client-ui-approval` 通过 `callId` 渲染 `conversation.approval.detail`
（`lib/client.js:43`），headline 用我们给的 `reason`。
也就是说**用户在批准前就能看到 `mode` 是 `resume` 还是 `remind`**。

于是 E1 的价值要重新评估：

- **若审批门（§9）已经装在 `add` 上**（`add` 是写操作，按 §8.2 就该审），
  模型走 `add {mode:"resume"}` 会弹审批，用户**看得见**它想建一条自动跑的任务，可以拒绝。
  **这时 E1 是冗余的** —— 审批本身就是那个决策点。
- **E1 仍有独立价值的情形**：用户容易**看漏** `mode` 这一行而顺手批准，
  而后果（自动开新会话、烧 token）不小。E1 让"能不能自动跑"变成**必须显式发生的第二步**，
  于是每次自动派发都对应**一次专门的批准**，而不是"批创建时附带批了自动执行"。

> **结论：E1 从"必需的前置"降级为"可选的加固"。**
> 建议**先上审批门（§9 + §12 的 H）**，E1 作为可选项交给你定。
> 不做也不构成漏洞 —— 前提是审批门确实装在 `add` 上。
> 若你觉得"批创建时顺手把自动执行也批了"不安心，就做 E1（**只改工具侧**）。

### E2 / E3（保留）

**E2：回合钩子只派发"用户创建的"条目。**
给条目加 `source: 'ai' | 'user'` 字段，钩子跳过 `ai` 来源的行。
比 E1 更彻底，但要改板文件 schema + 面板显示 + 调度规则，
且"AI 建的、用户后来认可的"要怎么算需要定义。**若做完 E1 仍觉得不够再考虑。**

**E3：给审批加"预授权"，让 AI 一次性申请"N 分钟内的写权限"。**
最省打断，但**把 fail-closed 变成了 fail-open 一段时间**，且要自己维护有效期。
**不建议起步就做。**

> 我的倾向是 **E1**：它用一个很小的改动关掉侧门，保持"一次授权只对一次调用有效"这条
> 现成的安全语义，且完全不碰已经稳定的调度代码。若将来发现"每次都要批"太打断，
> 再考虑 E3 —— 那时是**放宽**，比一开始就放宽再往回收容易。

### 另外两件实现前要想清楚的

1. **定时派发与回合钩子不在回合内**（§10.3），审批管不到它们。
   所以"审批"只能覆盖**模型主动发起**的写操作；系统自身的自动行为
   （到点派发、回合接续）要另外设计（比如 E1 之后，这些行为只作用于已存在且已获批的条目）。
2. **审批会打断回合**。`ask` 是同步等待裁决的，用户不在电脑前时回合会挂在那里
   （policy 为 `never` 时则确定性地拒绝）。这是"要不要在半夜跑自动任务"的直接取舍 ——
   值得和决策 C（并发上限）一起定。

## 12. **第二个坏消息：工具上的审批门可以被 HTTP 路由绕过**（实测）

§9 的方案有一个前提没验证：**审批装在工具上，但同一批写操作还有一个 HTTP 入口。**
本插件的宿主半边注册了 `/dsh-todo-board/api`，那个路由接受
`create` / `patch` / `reorder` / `remove` / `clearVerified` / `run` —— 也就是**全部写操作**。

### 12.1 实测

用**普通 shell 客户端**（不是浏览器）往那个路由发一个写请求：

```
POST /dsh-todo-board/api   {"action":"patch","id":"…","patch":{"note":"x"}}
→ status 200  {"ok":false,"error":"待办不存在"}
```

（故意用一个不存在的 id，所以没有改动真实板子；要点是**路由处理了写请求**。）

### 12.2 为什么这是致命的

1. **AI 有 shell**（`pwsh` / `bash` 工具）。模型完全可以不调 `todo_board`，
   改用一条命令打本机路由 —— **审批门根本不在这条路上**。
2. §9 的门只在 `tools/pre-execute` 上生效，而 HTTP 路由**不经过工具注册表**。
3. 根因：**本插件 0.9.0 复刻的围栏只做了半扇门。** 我把 `dsh-client-connection` 的
   `isTrustedApiRequest`（Host/Origin）照搬了过来，但**漏了它后面的
   `browserAuth.isAuthenticated`** —— 而后者才挡得住 shell 客户端。
   那句 "this fence is not an auth layer" 说的是 `isTrustedApiRequest` **那一个函数**；
   整个 `requestRejection` **是**鉴权层（Host/Origin + 浏览器凭据，缺一不可）。
   我当时读到了那半句注释就没有再往下核对调用点，这是我的疏漏。
4. 旁证：**`GET /` 对裸客户端返回 401，而我们的路由返回 200** ——
   首页走的是完整的门，我们只走了半扇。这个差异本来就该让我起疑。
5. 而且这不是理论问题：**本次会话里我就用这个路由做过管理操作**，
   并且为了满足"把安全任务放进 todo"的演示，又用它写入过一次（未经审批）。

### 12.3 结论：审批不能只装在工具上

> **任何"AI 不该做的事"，只要还有一个 AI 够得到的等价通道，审批就是装饰。**

所以本项的方案必须包含**通道收敛**，而不只是加一个 `ask`。§10 的侧门
（`add` + `mode`）只是**同一个问题的第一个实例**，不是全部。

**而这条通道的修法已经找到，且比预想的简单** —— 见下面的决策 H：
不必自造令牌，**改用 harness 自己的 `connection.requestRejection`** 即可，
它本来就是"Host/Origin + 浏览器鉴权"两件一起做。

### 12.4 这条对 0.9.0 的意义（不只是将来）

严格说，**这是 v0.9.0 的一个既有缺陷**，不是第 4 项才需要处理的：

- 0.9.0 我给两条路由加了围栏，方向对，但**只挡住浏览器那两类攻击**（rebinding / 跨站），
  **没挡住本机进程**；
- 0.9.0 同时开始把**日志**挂在同一条路由上 —— 也就是说，任何一个本机进程
  （包括 AI 自己）都能读到日志正文。日志含路径与其他插件的错误上下文（§design-log-view 3.2）。
- 当时我在文档里写的是"若有人把 host 绑成 `0.0.0.0` 会变成局域网可读"，
  并因为 DSH 自己拒绝 `0.0.0.0` 而认为风险有界 —— **这个推理漏掉了"本机进程"这一类**。

所以这一项应当作为 **v0.9.1 的修复**来做，而不是等第 4 项。
好消息是修法很小：把 `refuseUntrusted` 改为优先调用 harness 的门，
拿不到该服务时退回现在的复刻版本（保证在没有 `dsh-client-connection` 的部署里仍能用）。

### 决策 H：**已定 —— 是安全边界**（用户 2026-09-25）

用户明确：

> 我认为 H 应该是**安全边界**，而不只是防误触。

并且把权限模型的**边界**说清楚了（这比之前更精确）：

> AI 只有**申请编辑**的时候需要审批；后期都是我们现有的逻辑，自动派发下一个任务。
> **第一个任务的派发仍然要用户自己开始。**

即：

| 阶段 | 谁发起 | 要不要审批 |
| --- | --- | --- |
| AI 申请**写入板子**（创建 / 编辑 / 改模式目录标题 / 排序） | AI | ✅ **要** |
| **第一条**任务开始执行 | **用户** | 不需要（用户点 ▶ 就是授权本身） |
| 之后的接续（做完一条取同目录下一条） | 现有 `turn-stopping` 逻辑 | 不需要 —— **这正是它要自动做的事** |

这条边界很重要：它意味着**审批只挡"改板子"，不挡"跑任务"**。
所以 §12 的路由绕过要堵的是**写操作**，而不是把整条路由封掉 ——
面板的 ▶（用户点按）必须继续能直连。

### H1（采用，替代原先的"自造令牌"）：用 harness 自己的门

调研发现**不必自己发明令牌机制**：DSH 已经把这道门做好了，而且它做的正是**两件事**。

```
HostConnectionService.prototype.requestRejection(request)
  1. isTrustedApiRequest(request, trustedHosts)   → Host/Origin（防 rebinding / CSRF）
  2. browserAuth.isAuthenticated(request)          → 浏览器会话鉴权
  → 返回 403 / 401，或 undefined（放行）
```

它由 `dsh-client-connection` 的 `apply` 构造并注册为 **`connection`** 服务
（`super(ctx, "connection")`），所以插件可以 `ctx.get('connection')` 拿到，
`requestRejection` 是**公开方法**（不是私有的）。

**关键点**：本插件 0.9.0 复刻的围栏**只做了第 1 件**（当时只核对了 Host/Origin 那段），
第 2 件（浏览器鉴权）**漏了** —— 而漏掉的恰恰是挡住 shell 客户端的那一半。
这也解释了为什么 `GET /` 对裸客户端返回 **401** 而我们的路由返回 200：
首页走的是完整的门，我们的路由只走了半扇。

**所以 H1 的实现是**：把 `refuseUntrusted` 从"复刻 `isTrustedApiRequest`"改成
**优先调用 `ctx.get('connection').requestRejection(request)`**，
拿不到该服务时**退回**现在的复刻版本（部署里没有 `dsh-client-connection` 时仍要能工作）。

这样：
- **面板**（浏览器会话、带 DSH 的鉴权凭据）→ 照常放行，▶ 继续可用；
- **shell 客户端**（AI 用 pwsh/curl）→ **401，写不进去** —— 绕过通道从"约定"变成"机制"；
- 并且**自动跟着 harness 升级**：DSH 改了鉴权方式，我们跟着变，不需要重新复刻一次。

**仍需你确认的一点**：这让路由写操作**要求浏览器凭据**。
如果你有"用脚本/命令直接往板子里加待办"的习惯（比如从别的工具调用），
那个用法会被一起挡掉 —— 需要的话可以给一个显式的本地豁免（例如读 `DSH_*` 环境里的令牌），
但那又会重新打开一条通道，所以**默认不做**，等你确认。

> **2026-09-26 落地后的实况**：脚本通道确实被挡掉了，已按"默认不做"实施（README「安全」§三 写明了代价）。
> 另外拿到了一条当时只是推断的证据：GUI 自己的 WebSocket 通道 `/api/remote.mux`
> 走的就是同一个 `requestRejection`（`dsh-api-gateway/lib/index.js:463`），
> 所以"浏览器带着 cookie，面板不受影响"是**同一条门放行的结果**，不是猜测。

### 备选（仅在 H1 不可行时）

**H2：只给写操作加进程内令牌**（我原先的建议）。面板启动时从 host 取短期令牌，
写请求必须带。比 H1 弱（令牌要自己管生命周期），但同样只挡外部客户端。
**现在不需要了** —— H1 更彻底且更省事。

**H3：接受现状，定义"本机即可信"。** 已被用户否决（H 是安全边界，不是防误触）。

### 与本文原先写法的两处偏差（都是有意为之）

1. **`done` / `reopen` 不在审批范围内**（§8.2 的表格没写它们）。
   理由是那条循环正是用户要的自动化：它在 `danger-full-access`（policy `never`）下会被**每次拒绝**，
   自动接续会当场断掉；而 `pendingInDir` 把 `aiDone` 的行视为不在队列里，勾选本身启动不了任务。
   即：**审批挡"改板子"，这两个动作在语义上是"勾自己的左勾"，属于跑队列那一侧。**
2. **未知动作也走 `ask`**，而不是"没匹配上就放行"。一个新写的写动作忘了进白名单，
   必须失败关闭 —— 这正是白名单（而不是黑名单）存在的原因。

第 4 项的三个动作各自带一条自己的守卫，都来自"模型会做的事"而不是"代码能做的事"：

| 动作 | 守卫 | 为什么 |
| --- | --- | --- |
| `update` | 先整体校验，再落笔 | 一个字段不合法就整条拒绝。半途生效会让模型和刚批准的用户都说不清改了什么 |
| `reorder` | 只接受同一目录内的 id，未知/重复整条拒绝 | 面板按目录分组、每个队列各走各的，跨目录列表会悄悄重排用户没打算动的队列 |
| `dispatch` | 只有「未派发」的能派发 | 与面板 ▶ 的启用条件一致（不另造第二套规则）：重复派发是重复劳动，已完成的不是活 |

### 已定与没落的

- **决策 E1：不做 —— `add` 保留 `mode`**（用户 2026-09-26）。理由与 §11 里用户反对"新建一律 remind"
  的那条一致，而且双向成立：**用户自己**要能一次建出"续跑 / 新会话"的待办，

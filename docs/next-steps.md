## 第 3 项：剪贴板粘贴图片 —— 已实施（v0.8.0）

用户确认：**只处理图片，文本走原有输入**；并追加要求：**原来的「📎 图片」选文件按钮删掉**。

实施结果：新增框 `Ctrl+V` 直接粘贴成附图（最多 4 张），选文件按钮与其 CSS 一并删除。
关键约定与陷阱（都已在测试与变异体里钉住）：

- **只有真的带图片时才 `preventDefault`** —— 文本粘贴必须原样进 textarea。这是本功能的核心契约：
  写待办的主要方式是粘文字，不能为了附图把它弄坏。
- **剪贴板图片可能不带 MIME 类型**（部分截图工具），要按扩展名兜底，且只认 host 认可的那四种；
  扩展名不认识的既不当图片也不拦截。host 对 `mediaType` 是严格校验的，空值会被当成「(未声明)」拒收。
- 剪贴板的 `files` 和 `items[].getAsFile()` **两个面都要读**，有些粘贴只出现在其一。
- 上限处理：粘满为止并告知具体张数，不静默丢弃、不整批拒绝。
- 输入框空着时不显示任何常驻提示；附图区只在真的附了图后出现（显示 `已附 N / 4 张`）。
- 这些**平台形状**由 `tools/check-browser.mjs` 用真实 `DataTransfer` / `File` / `ClipboardEvent` /
  `FileReader` 在 headless Chrome 里验证 —— Node 套件只能验证插件逻辑，验证不了浏览器行为。

## 第 2 项：后台日志 —— **已实施（v0.9.0）**，方案见 `design-log-view.md`

用户要求：**不用 DSH 的设置栏**，在 TODO 栏加一个小按钮，点击把面板切到日志页；
平时不暴露给用户，出错时能给开发者调试线索。

用户拍板：**默认只记本插件**（`levels: { 'dsh-todo-board': 3, default: 0 }`）。

实施结果一句话版：**标题栏 `⚙` 按钮 → 同一个浮窗内切到日志页**；
错误/警告到达时按钮上亮一个小圆点（打开即清）；级别/来源/关键字三种过滤 +
复制 / 导出 .txt / 清空显示。**日志正文只在视图打开时才随轮询返回**，
关闭时轮询负载与改动前逐字节相同。

三条最值得记住的：

> **1. `ctx.logger.buffer` 不能当日志源** —— 它没有 `levels`，门控默认 `INFO`，
> 于是 `warn` 和 `debug` 全被丢掉（实测只收到 `error` / `info`）。必须自己注册 exporter。

> **2. 脱敏是承重结构，不是加固** —— 密钥从来不是被某处不小心的 `logger.warn(secret)` 记下的，
> 而是夹在**别人构造好的消息**里（通常是 Config 校验失败时的 `Error.message`）。

> **3. 这两条路由原本不在 DSH 的 `/api` 信任围栏内** —— 实施前实测：不带任何凭据就能
> `GET` 出整个板子，且 `text/plain` 的跨站 POST 能直接改板。**日志落地前必须先补围栏**，
> 否则等于给一条无鉴权、可被跨站读取的路由挂上诊断信息。详见 §5.3。

## 第 4 项：MCP / 规则 —— 安全前置已实施（v0.9.1），方案见 `design-ai-dispatch.md`

> **2026-09-26 更新**：本项的**主体已在 v0.9.1 落地** —— 已定的两条（审批门、通道收敛）、
> 途中发现的**模型工具注册竞态 bug**，以及模型侧的三个写动作（`update` / `reorder` / `dispatch`），
> 清单见 `design-ai-dispatch.md` §14。仍未做的是**决策 E1**（`add` 是否保留 `mode`，留用户定）、
> `remove` / `clearVerified`（删除类动作没交给模型），以及 §13 里其余的待拍板项
> （并发上限、长任务分段、入口形态）。

用户目标（原话要点）：

> 用户通过一个入口/一个提示词，能让他的 DSH 的一个会话，自动的使用我们的工具，
> 把长任务/分段式任务/多个任务分配给其他会话，也就是允许 AI 自己编辑 todo 和派发任务。

**用户在 2026-09-25 补充的权限要求（本项的定调）**：

> 我希望 AI 在修改 todo 面板（当前功能之外的所有功能，包括创建 todo、编辑、
> 更改模式/目录/标题/排序、派发）时，**需要明确向用户申请权限**。之后就可以写入 todo 面板，
> 然后需要用户开始执行，之后就是我们之前的逻辑，AI 继续执行 todo 面板里的其他 todo，
> 直到完成所有 todo。

即确定了两条：**写板要显式申请权限**（不是决策 B1 的"AI 只能派发用户已认可的"，
而是更严格的"任何写操作都要先问"），以及**执行仍由用户发起**。

关于"MCP"的澄清（本次调研结论，见 `design-ai-dispatch.md` §7）：
**本插件不该走 MCP** —— MCP 工具在 DSH 里同样注册进 `ctx.tools`，
模型侧与原生工具**完全等价**（同样 token、同样 KV cache 行为），差别在执行时能拿到什么：
MCP 那次调用**只传 `{name, arguments}`**，拿不到 `exec.agent`、cwd、session，
而本插件的核心语义（哪块板子、开新会话、preset、附件库）全押在这些东西上。
另外全树**没有任何 MCP server 端实现**，DSH 只做 client。

**需要你先拍板的**：并发上限、长任务分段用"多条顺序待办"还是"父子待办"、
以及权限申请的具体形态（每次弹窗确认 / 会话级授权 / 其他）。

### 2026-09-25 二轮调研（见 `design-ai-dispatch.md` §9–§11）

**好消息：权限不用自己造。** DSH 有原生审批通道 —— `tools/pre-execute` 返回 `{kind:'ask'}`，
由 `dsh-user-approval` 裁决，**没有审批通道时降级为拒绝**（fail-closed，一次授权只对一次调用有效）。
本机 `dsh-base` 已挂审批服务（policy 默认 `ask`）、`dsh-web-app` 已挂审批 UI —— 连界面都不用我们画。
我在真实 `ToolRuntime` 上实测：**读放行、写被拦，模型绕不过去**（不是提示词约定，是注册表级的门）。

**坏消息：AI 今天就已经能自己派发。** `add` 接受 `mode`，而回合结束钩子会自动派发同目录下
第一条非 `remind` 条目 —— 实测模型调一次 `add {mode:"resume"}`，回合结束时任务就被派走了，
**全程不需要用户任何动作**。所以只给将来的 `dispatch` 动作加审批，等于"给一扇已经开着的门
旁边再加一把锁"。这条侧门**今天就在生产里开着**，不是本项引入的，
但**封它（决策 E）是本项实现的先决条件**。

顺带实测到一条实现约束：`approval.request()` **必须在回合内**（否则抛错，因为审计事件要成对落在回合里）。
所以**定时派发与回合钩子本身管不到审批** —— 审批只能覆盖"模型主动发起"的写操作。

**还有第二条绕过通道（同一次调研，`design-ai-dispatch.md` §12）。** 审批装在**工具**上，
但同一批写操作还挂在 `HTTP 路由` 上，而那条路由**接受任何本机客户端的写请求**
（`Host` 回环即放行 —— 它是防 rebinding/CSRF 的浏览器围栏，**不是鉴权层**）。
我用普通 shell 客户端实测：`POST /dsh-todo-board/api` 的写请求被正常处理。
**AI 有 shell，所以它能绕过工具上的审批门。**

两条合起来的结论：**本项真正的第一件事是"通道收敛"，而不是加一个 `ask`** ——
只要还有一条 AI 够得到的等价写入通道，审批就是装饰。

**需要你先拍板的（更新）**：**决策 H（路由绕过怎么办，见 §12）**、
**决策 E（侧门怎么封）**、决策 A（派发目标）、决策 F（审批粒度）、
并发上限、长任务分段方式。
决策 E 建议 **E1**：`add` 不再接受 `mode`（新建一律 `remind`），改模式必须走要审批的 `update` ——
改动极小、不碰已经稳定的调度代码，且保住"一次授权只对一次调用有效"这条现成语义。
决策 H 建议 **H1**：给路由的写操作加一道**只有面板拿得到的进程内令牌**；
若你觉得在单用户本机上不值得（H3 也自洽），那就**把 §8 的权限模型诚实降级为"防误触"而不是"安全边界"**。

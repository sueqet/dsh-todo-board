# 方案：长任务先问一句「要不要用 TODO 板拆开按步做」

> 状态：**已实施（v0.11.0）**。本文保留为设计与依据记录；实施结果、与本文的偏差、以及
> 变过的决策见文末 §7。
> 相关：`design-ai-dispatch.md`（第 4 项：AI 写板子 + 审批门）、`next-steps.md`。

---

## 0. 结论先行

需求是两件事，其实是同一条链子的两端：

| # | 谁发起 | 要什么 | 落在哪里 |
| --- | --- | --- | --- |
| A | **模型** | 用户丢来一个长任务/多阶段任务时，**先问一句**要不要用 TODO 板拆成步骤，而不是闷头开干 | ① 提示词段落里加一条常驻规则；②（可选加固）`agent/pre-step` 钩子在"看起来像长任务"时**确定性地**提醒一次 |
| B | **用户** | 用户想主动让模型拆分时，有**一个入口**和**一段可复制的模板提示词** | ① `/todo <目标>` 命令：直接注入模板；② 注册一个**运行时 Skill**（手册 + 模板全文），模型可 `skill` 加载、用户可 `/todo-board-planning` 直达；③ README 里给可复制的模板 |

**外加一条必须先解决的前置问题**：现在 `add` 是**一次调用一次审批**，拆 8 步 = 8 个审批框。
不解决它，这个功能的体验会碎成一地 —— 所以方案里包含**批量创建**（一次调用建完整份计划，一次审批）。

推荐落地顺序（每一步都能单独交付、单独回滚）：

1. **批量创建**（`add` 支持 `items`）—— 前置，前后端都能测。
2. **提示词段落加规则** + **模板提示词**（README + 一处代码常量）—— 零机制，立刻可用。
3. **`/todo` 命令** + **运行时 Skill** —— 给用户主动入口、给模型按需手册。
4. **`agent/pre-step` 确定性提醒** —— 只有在你选"要更可靠"时才做。

## 1. 现状：已经有什么（本次不改但要利用的）

- **提示词段落**：插件已经挂了 `systemPrompt` 段落（`order: 150`），每个会话都看得到，
  里面已经写了"列表从上到下就是执行顺序""做完一条勾一条，再取同目录下一条，不要停下来等用户"。
  → **新规则加在这里最省事，也最一致。**
- **模型工具 `todo_board`**：`list / add / done / reopen / note / schedule / update / reorder / dispatch`。
  其中 `add` 已经支持 `note` / `schedule` / `images` / `mode`。
- **审批门**：`list / done / reopen` 不问，其余写操作一律弹 DSH 原生审批框，
  且**一次授权只对一次调用有效**。`done` 不问，所以"做完一条勾一条"的自动接续不会被审批打断。
- **回合结束钩子**：`agent/turn-stopping` 会把**同目录下最上面一条未派发、且非 `remind`** 的条目派发出去
  （`resume` → 发进当前会话；`newSession` → 开新会话）。这条决定了"计划建好后会不会立刻自己开始"。
- **面板**：双勾选、已完成列表、备注（把 note 显示出来正是为这件事铺的路 —— 模型写进 note 的验收标准/上下文，
  用户派发前看得见）。
- **DSH 侧可用的三件套**（本轮调研，均已在本机 profile 里挂好）：

| 能力 | 接口 | 关键事实 |
| --- | --- | --- |
| Skill | `ctx.skills.register({name, description, whenToUse, content, source, invocation})` | 运行时注册。**`content` 与 `source` 必填**（加载时会校验）；`invocation: {modelInvocable, userInvocable}` 决定模型能不能自己加载、用户能不能 `/名字` 直达。目录里只显示 name/description/whenToUse —— **手册正文不常驻上下文** |
| 命令 | `ctx.commands.register({name, description, input: {hint, attachments}, handler})` | `handler(invocation)` 拿到 `{agent, rawInput, attachments, signal}`；`agent.followup(消息)` 就能把一段提示词作为用户消息注入。名字规则 `^[a-z][a-z0-9_-]*$`，所以 `/todo-plan` 合法。先例：`dsh-command-goal` |
| 步骤钩子 | `ctx.on('agent/pre-step', ({agent, messages}, next) => …)` | waterfall：`next()` 之后能拿到 `{kind:'enter', messages}`，**往 messages 里追加一条消息**就能把提醒塞进这一步的上下文。先例：`dsh-hooks-claude-code` |

- 提醒工具：模型有 `ask_user_question`（结构化选项按钮），适合"要不要拆 / 怎么执行"这种二选一。

## 2. 三条硬约束（都是实测/读源码得来的，决定了方案形状）

### 2.1 一次审批 = 一次调用 → 必须批量创建

`add` 每调用一次就弹一次审批。要拆 8 步，就得让模型连点 8 次审批，
用户点 8 次"允许"，任何一次点错都会留下半份计划。**批量是功能的一部分，不是优化。**

### 2.2 `remind` 和 `resume` 的语义差，正好卡在"第一条由谁开始"

- 全 `resume`：计划写入后**回合一结束就自动派发第一条**（钩子干的），之后一条接一条。
  好处：真的是"按步执行"。代价：**与用户早先定的"第一个任务的派发仍然要用户自己开始"冲突**。
- 全 `remind`：写入后**谁也不动**，用户点面板 ▶ 开始第一条。代价：**自动链断了** ——
  钩子只认非 `remind` 的条目，第一条跑完后它找不到下一条，用户得为每一步点一次 ▶。

这不是实现细节，是"这个功能到底怎么用"的产品选择，所以放在 §5 让你拍板。

### 2.3 提示词段落的规则是"软"的

模型在兴头上很容易直接开干。"常驻规则 + 模型判断"能覆盖大部分情况，但不是保证。
要更可靠只有一条路：**在用户消息进来的那一刻（`agent/pre-step`）由代码判断并提醒**，
代价是启发式会误报（把一句话的活儿也当成多阶段任务 → 模型多问一句）。
误报的代价很低（多问一句），漏报的代价也不高（就是现在的行为），所以这条是"可选加固"，不是必需。

## 3. 推荐方案

### 3.1 提示词段落加两条（改 `lib/index.js`，约 6 行）

在现有段落末尾补：

```
- **用户给的是多阶段/长任务时，先问一句再动手**：如果这件事明显要分几步做，而当前目录下**还没有**待办，
  先用一句（或 ask_user_question）问用户：要不要用 TODO 板拆成步骤、按顺序执行？不要闷头开干。
- 一旦当前目录下**已有**待办，就按上面的规则继续做，不要再问。
```

第二句是防唠叨的关键：**板子非空就不再问**，避免每轮都问一遍。

### 3.2 批量创建：`add` 支持 `items`

工具参数增加一个可选数组（一次调用、一次审批、一份计划）：

```
items: [{ title, note?, mode?, schedule?, images? }, …]
```

- 与单条 `add` 共用同一套校验/入库，`items` 存在时 `title` 可省略；两者同时给以 `items` 为准。
- 审批理由写成计划全文（例：`新增计划（6 步）：1) … 2) … 3) …`），
  这样**审批框里就能读到整份计划**，而不是只看到"新增待办"。
  **实现时要在真 GUI 上核对审批框对长理由的呈现**（它是标题行 + 详情，可能自己会折/截）：
  若真被截，就把计划正文放进详情位，理由只留"新增计划（N 步）"。
  无论如何**不静默截断我们的文本** —— 我们这一侧要么给全，要么明写 `…（共 N 条，余下见面板）`。
- **条数上限 20 条**（超出整批拒绝并说明），防止一次审批批掉一屏计划；分批让用户看得见代价。
- 返回一条汇总 + 全部新条目的 `todos`，模型据此向用户复述"建了哪几步"。

### 3.3 模板提示词（一处定义，两处露出）

代码里放一个常量 `PLAN_TEMPLATE`，`/todo` 命令与 Skill 都用它，README 复制同一份；
再加一条测试断言 README 里的模板与常量**逐字一致**（这类"两处文本会漂移"的坑，本仓库已有先例
`check-fence-parity.mjs`）。

正文草案（用户可整段复制）：

```
用 TODO 板把这件事拆成可执行的步骤，然后按顺序做。

【目标】<一句话说清最终要什么>
【边界】<不要做什么、必须遵守什么>
【完成标准】<怎么算做完；能跑命令/看结果最好>

拆分要求：
1. 每条一句话、彼此有顺序、能独立验收；一条只交付一件事，别把两件事塞一条；
2. 先给我看拆分结果，我确认后再写进板子；我说改就改；
3. 每条待办的备注（note）里写清：验收标准 + 已知的坑/前置条件；
4. 建好后用哪种执行模式、以及要不要立刻开始，按我这次的回答来（见下）。

执行要求：
5. 开始后每做完一条，立刻把那条勾成「AI 已完成」，再取同目录下一条继续，不要停下来问我；
6. 中途发现要加步骤，用 update/新增告诉我，别自己闷着改范围。

（我不特别说的话：默认拆 3–8 步。）
```

### 3.4 `/todo <目标>` 命令（用户主动入口）

- 语义：把模板 + 目标作为一条用户消息注入当前会话（`agent.followup`），模型随即开始规划。
- `/todo` 不带参数：注入模板并把 `<目标>` 留成占位符，让用户补。
- 命名：`/todo`（短、贴合插件）还是 `/todo-plan`（不抢通用名）见 §5 决策。
- 附注：命令 handler 在会话内执行，**不经过审批门**（它不是模型发起的写操作）；
  真正写板子那一步照样要审批 —— 这条边界不能破。

### 3.5 Skill：`todo-board-planning`（手册 + 模板，按需加载）

- `whenToUse`：用户在给多阶段任务、或用户说"拆一下/规划一下/用 TODO 板做"时。
- 正文：什么时候该拆、怎么拆（粒度、顺序、验收标准进 note）、怎么建（批量 `add`）、
  执行模式怎么选、怎么收尾（勾完成 → 取下一條）、模板全文。
- 用户可用 `/todo-board-planning` 直达（`userInvocable`），模型可自己 `skill` 加载（`modelInvocable`）。
- 好处：手册不常驻上下文，只有真要用时才进；插件降级也安全（拿不到 `skills` 服务就不注册）。

### 3.6 可选加固：`agent/pre-step` 提醒

触发条件（**全部**满足才提醒，且**每个会话最多一次**）：

1. 这一步带进来的用户消息是"新话"（不是工具结果、不是插进来的通知）；
2. 当前工作目录下**没有未完成的待办**；
3. 消息看起来像多阶段任务：长度 ≥ 200 字，**且**有明显的枚举/阶段标记
   （`1.` `2.` / `- ` / `首先/然后/最后` / `第一步` 等 ≥ 2 处）。

提醒内容是一句短上下文（不是用户消息）：`这条请求看起来是多阶段任务：可以先问用户要不要用 TODO 板拆成步骤（ask_user_question），不要直接开干。`

## 6. 风险与不做的事

- **误报**（D6）：一句话的活儿也被问"要不要拆"。缓解：阈值保守、每会话一次、板子非空不问。
- **批量创建的审批疲劳变体**：一次审批批掉 8 条，用户可能不看细节就批。缓解：审批理由里列出每一步，
  且计划**先给用户看过**（模板第 2 条要求"确认后再写"）。
- **`resume` 自动开跑的惊喜**：D1 选①时，用户确认计划后第一条会自己开始。这是设计意图，
  但必须在确认框里写清楚（`就按这个做（立刻开始）`）。
- **不做**：不引入"计划"这种新对象（父子待办、进度树都不做，仍是平铺待办 + note）；
  不加面板按钮（面板已够满）；不动"第一条由用户开始"之外的其他权限边界；
  不把模板做成硬编码字符串散落在多处（只留一处常量 + README 断言）。

### 与本文的三处偏差（写完才发现的，都比原计划更对）

1. **`/todo` 不带目标 → 报用法错误，而不是注入模板。** 原计划是"注入模板留占位符让用户补"，
   但注入是直接发给模型的 —— 模型会把 `【目标】<一句话说清最终要什么>` **当成真目标**去拆。
   一个会静默做错事的命令比一个要参数的命令糟得多，所以改成 `kind:'error'` + 用法提示。
2. **批量校验改成三段式（校验全部 → 入库图片 → 写行）。** 原计划只是"先校验再写"，
   但图片入库本身是 `await`，如果边校验边入库，第二条图片失败时第一条的附件**已经存进附件库了** ——
   板子是干净的，附件库不是。现在三个阶段严格分开。
3. **`looksStaged` 不做正则拼接。** 原计划用 `new RegExp(pattern.source, …)` 重建带 `g` 的标志，
   实际上那五个模式本来就带 `g`，重建纯属多余且有陷阱（`lastIndex` 状态）。直接 `body.match(pattern)`。

### 变异检查抓到的两个测试漏洞（值得单独记）

`check-host-guard.mjs` 现有 **15 个**变异体。这一轮新加的 6 个里，**头一次跑就有 2 个没被抓住**：

- **"短而结构化的消息不该触发"测得太假**：我原来的负例是 `'1. 改个错别字 2. 提交'` ——
  它太短，短到**长度阈值和标记计数会同时拦住它**，所以把长度阈值删掉也照样绿。
  改成三条带编号的行（标记足够、长度不够），才真正只压住长度那一条。
- **"整批不落库"的变异体写错了位置**：我最初把变异打在 `staged.push` 之后，而校验失败时
  **根本走不到那一行**，所以变异体是死的（跑完等价于没改）。换成"把 `return` 改成 `continue`"
  ——那才是真正的风险形态：跳过坏的那条、把好的写进去，用户拿到的是**另一份计划**。

**教训**：变异体没被抓住时，先怀疑测试和变异体本身，不要先怀疑"这个行为不重要"。
这两次都是测试的漏洞，不是代码的漏洞 —— 而这正是这个守卫存在的意义。
